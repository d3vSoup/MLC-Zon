# Reproduce QTpies M5 → `sub12_m5_shift`

**What this reproduces**
- **The model:** M5 (`qtpies-m5`), with train OOF F0.5 **0.98820** in the density-matched (DROP16) world.
- **The submission:** `submissions/sub12_m5_shift/matching_results.tsv`, with 1,732,544 rows, 5,731,902 matched IDs and SHA-256 `33ed43ab1c4471c515a0fb1e506020d0906067ce69acb4c4de2cd55926615645`.

**Code version:** `code/business_entity_resolution/` at `er-pipeline` `544d5df`, which is the same code as `main` `7240980` on MLC-raZON.
- Checked with `git diff`: since the snapshots the M5 chain ran with (`38e0b5e` for CE-4, `ab98fa8` for CE-2 and M5), code that runs on Kaggle has changed only additively. New batches and new env switches were added, and their defaults are unchanged.
- Otherwise only `calibrate.py` changed, and it runs on the laptop (§3).

## 1. Laptop: data preparation

Put the challenge data at `<repo>/student_resource/dataset/{train,test}/*.tsv`.

**Normalise.** Run from `code/business_entity_resolution/src`:

```
export PYTHONUTF8=1 BER_WORK=<repo>/work2
python norm.py
```

With no arguments, `norm.py` runs the `admin` job and then all six file jobs. It:
- learns `translit.parquet` from train true pairs, if that file is missing;
- learns `admin_{train,test}.parquet` label-free, per split;
- writes `n_{split}_s{1,2,3}.parquet`;
- as a side effect, caches the raw TSVs as `{split}_s{k}.parquet` and writes `gt_pairs.parquet` in `BER_WORK`.

**Private Kaggle datasets.** `kaggle datasets create` makes datasets private by default. Never make them public.

| Dataset | Contents | Used by |
|---|---|---|
| `razanml/qtpies-er-norm` | `n_*.parquet`, `translit.parquet`, `admin_*.parquet`, `gt_pairs.parquet` (from `work2`) | Every kernel |
| `razanml/qtpies-er-data` | Raw `{train,test}_s{1,2,3}.parquet` and `gt_pairs.parquet` | CE-2 (raw text) |
| `razanml/qtpies-er-cand-test` | Test candidates for France and India, named `cand_test__{France,India}_{nnn}.parquet`: 6 France and 19 India files. The kernel template maps `a__b` to `a/b`. | `feats_test` and every batch that lists it in `EXTRA_DATASETS` |

## 2. Kaggle job chain (DAG)

Run every command from `code/business_entity_resolution/` as `python kaggle_runner.py <command> <batch …>`.

**How `chain` works:**
- `chain b1 b2 …` pushes each batch in turn. It retries every 60 s, for up to 2 h, while Kaggle's limit of 5 concurrent CPU sessions is full, then waits for all of the batch's kernels to finish before moving on.
- `=b` means wait for batch `b` without pushing it.
- `push`, `status`, `fetch` and `wait` also exist.
- Each kernel embeds the current `src/` as a tarball, links its inputs, runs its jobs, and exports newly written files even if a job fails.
- Kernels read earlier kernels' outputs through `kernel_sources`, so **the order matters**.

| Step | Command | Kernels (`qtpies-…`) | Hardware | Batch settings | Key outputs |
|---|---|---|---|---|---|
| 1 | `chain block`, then `push block_gpu` | `blk-train-india-{0,1,2}of3`, `blk-train-us-{0..3}of4` | CPU; `block_gpu` re-pushes train-US shards 2–3 on the GPU pool | — | `cand_train/*.parquet`: 42 chunks, 168.7M pairs |
| 2 | `chain block_test_us` | `blk-test-us-{0,1,2}of3` | CPU | — | `cand_test/US_*.parquet` |
| 3 | `chain feats_test feats_train` | `ft-test-{0..3}of4`, `ft-train-{0..4}of5` | CPU | — | `F_test/*`; `F_train/*` at natural density |
| 4 | `chain ce_train` | `ce-train-{0,1}` | GPU T4×2 | — | `ce_fold{0,1}/` (CE-1) |
| 5 | `chain model` | `model` (M1: `run.py train`, `train2`, `predict`) | CPU | — | M1 `oof_m`, `pred_test_m` |
| 6 | `chain ce_score` | `ce-score` | GPU | — | CE-1 `ce_train.parquet` / `ce_test.parquet` |
| 7 | `chain ftd_train` | `ftd-train-{0..4}of5` | CPU | `BER_DROP=16` | `F_train/*`, density-matched |
| 8 | `chain m2_fit1 m2_pred` | `m2-fit1`, `m2-pred-{0..4}of5` | CPU | `BER_DROP=16` | `m_fold{0,1}.txt`, `oof_m_part*`, `pred_test_m_part*` |
| 9 | `chain m2_s2` | `m2-s2` (`gather1`, `train2ce`, `predictce`) | GPU pool (CPU work) | `BER_DROP=16 BER_POOL=12000000` | **`oof_m.parquet`, `pred_test_m.parquet`**: M2's stage 1, read by every CE-4 and CE-2 kernel |
| 10 | `chain ce4_train ce4_score` | `ce4-train-{0,1}`, `ce4-score-{train,test}` | GPU | train `BER_CE_HARD=1`; score `BER_CE_BAND=0.002,1.01` | `ce_fold*`; `ce_train.parquet` / `ce_test.parquet` (CE-4 scores for every stage-2 pair) |
| 11 | `chain ce2_train ce2_score` | `ce2-train-{0,1}`, `ce2-score-{train,test}` | GPU | `BER_CE_HARD=1 BER_CE_RAW=1 BER_CE_TAG=ce2`; score also `BER_CE_BAND=0.002,1.01` | `ce2_fold*`; `ce2_train.parquet` / `ce2_test.parquet` |
| 12 | `chain m5` | `m5` (`gather1`, `train2ce`, `predictce`) | CPU | `BER_DROP=16 BER_POOL=12000000 BER_GENERIC=1` | `output/s2ce/{matching_results,candidate_pairs}.tsv`, **`pred_test_s2ce.parquet`**, **`oof_s2ce.parquet`** |

**Notes on the chain:**
- **Step 1:** the `block` batch also defines the 7 test shards. Historically, the France and India test shards ran on the laptop (§1) and the US test shards ran in step 2, under the same kernel names. With the current settings, `feats_test` reads the France and India test candidates from the `qtpies-er-cand-test` dataset, not from kernels.
- **Steps 4–6** (M1 and CE-1) do not feed M5's features. But `m2_s2` lists `qtpies-ce-score` as an input, so those kernels must exist for step 9 to run as written.
  - A leaner alternative: remove `"qtpies-ce-score"` from `m2_s2`'s input list. The `gather1` output that M5 needs does not change.
- **Not part of M5's lineage:** `m3`, `m3t` and `m4` (M3, the tuning run and M4).
- **The commands as originally run:**
  - M2: `chain =ftd_train m2_fit1 m2_pred =ce_score m2_s2`
  - M4: `chain ce4_train ce4_score m4`
  - M5: `chain =ce4_score ce2_train ce2_score m5`
- **Observed wall times:**

  | Batch | Time |
  |---|---|
  | Train blocking (7 shards) | ~14 min |
  | Feature shards | ~15 min |
  | `m2_pred` | ~25 min |
  | `m2_s2` | ~35 min |
  | CE-4 train + score | ~2 h 15 min |
  | CE-2 train | ~3 h |
  | CE-2 score | ~1.8 h |
  | `m5` | ~30 min |

## 3. Fetch and calibrate → `sub12_m5_shift`

From the repo root:

```
kaggle kernels output razanml/qtpies-m5 -p runs/qtpies-m5 --file-pattern "pred_test_s2ce\.parquet$|oof_s2ce\.parquet$"
python code/business_entity_resolution/finalize.py qtpies-m5 sub10_m5 s2ce        # optional: raw M5 decode + validator

cd code/business_entity_resolution
BER_WORK=<repo>/work2 BER_DROP=16 PYTHONUTF8=1 python memguard.py 3 python src/calibrate.py \
    ../../runs/qtpies-m5/pred_test_s2ce.parquet ../../submissions/sub12_m5_shift ../../runs/qtpies-m5/oof_s2ce.parquet

cd ../../student_resource
python utils/validate_submission.py --matching ../submissions/sub12_m5_shift/matching_results.tsv --test-dir dataset/test
```

- **`BER_DROP=16`** must match the density world of the OOF file.
- **The third argument (the OOF file)** switches `calibrate.py` to its data-derived mode: a country counts as seen if it appears in the train OOF. `memguard.py` is optional; peak RAM is about 2.3–3.5 GB.
- **Expected console output:**

## 4. Determinism: what is bit-exact and what isn't

**Bit-exact (checked):** `sub12` from the saved `pred_test_s2ce.parquet` and `oof_s2ce.parquet`. Both `calibrate.py` and `decide.py` are deterministic.

**Deterministic given the pins:**
- normalisation;
- the folds (`hash(si, 42) % 2`) and the dropped S1s (`hash(si, 49) % 100 < 16`), with polars 1.44.2;
- the blocking candidates. Top-15 selection could break *exact* score ties differently at a different thread count.

**May differ slightly on a rerun from scratch:**
- LightGBM training: multi-threaded (4 threads on Kaggle) and `deterministic` is not set;
- the cross-encoders: fp16, `DataParallel` over 2 GPUs, and non-deterministic cuDNN kernels.

A from-scratch rerun should land within about 1e-4 of the OOF F0.5, but will not produce a byte-identical submission.
