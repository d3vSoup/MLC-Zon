# Business Entity Resolution: reproduction

Regenerates `output/candidate_pairs.tsv` and `output/matching_results.tsv` from the challenge data.
No external data, APIs or geocoding are used; the network is used only for `pip` and pretrained model downloads.
This folder holds code only: every intermediate file is regenerated by the steps below, which name its location and
the md5 it had in our run.

## Layout expected

```
<root>/                       # the zip root (or student_resource/)
  dataset/{train,test}/*.tsv  # challenge data (not shipped)
  utils/validate_submission.py
  output/                     # written here
  work/                       # caches (created)
  code/business_entity_resolution/{src,README.md,requirements*.txt}
```

Paths are set in `src/configs/default.yaml`, relative to `<root>`. Override the root with `BER_ROOT=/path`.

## Overview

| Step | Code | Hardware | Produces |
|---|---|---|---|
| A. pipeline A + blend | `src/run_all.sh` (package `src/ber/`) | CPU, 16 GB RAM + swap | `output/candidate_pairs.tsv`, the blend and single-pipeline files step D reads |
| B. cross-encoder scores | `src/gpu/ce_train_predict.py` | GPU (2x T4) | `src/ce_scores/` (input of A) |
| C. pipeline C (QTpies) | `src/razan/` (see `src/razan/README.md`) | Kaggle CPU + GPU, laptop | stage-2 p and id maps in `src/razan/` (inputs of A and D) |
| D. final fuse | `src/razan/src/fuse.py`, `merge_by_country.py` | CPU, ~5 GB RAM, minutes | `output/matching_results.tsv` |

**Run order:** C up to M10 (C.1-C.4 in `src/razan/README.md`) and B -> A -> C: export, M11, M11h -> A: second blend -> D.

## Environments

- `requirements.txt`: step A (Python 3.11, all transitive pins).
- `requirements_ce_gpu.txt`: step B, on the Kaggle GPU image.
- `requirements_qtpies.txt` (+ `requirements_qtpies_gpu.txt` for its cross-encoders): steps C and D, Python 3.12
  (polars exactly 1.44.2). It is a separate environment because its pins conflict with step A's.

## B. Cross-encoder scores (GPU)

`python -m ber.cli ce_export`, then `src/gpu/ce_train_predict.py --half 1` and `--half 2` (xlm-roberta-base, MIT;
2x Tesla T4 on Kaggle, torch 2.10.0+cu128: 5.61 h and 5.80 h), then `python -m ber.ce_ingest <dir_half1> <dir_half2>`.
Output: `src/ce_scores/ce_scores_train.parquet` / `ce_scores_test.parquet` (s1, cand, ce_p; md5 in our run
`afff2a01b42fbf88e1b6d715fe014cff` / `65ba8a9e2896aa771a49f176402970b6`). The scores are keyed by entity ids, so step A
uses them whatever the row order of its candidate list.

## C. Pipeline C (QTpies)

`src/razan/README.md`: normalisation, blocking, stage 1, cross-encoders, twin world and stage 2 (M9) on private
Kaggle kernels, then stage 3 (M10 / M11) and M11h on a laptop. It writes the M10 bundle into `src/razan/` (the blend
input of step A), M9 test p into `src/razan/fuse/m9/` and, after step A, M11h into `src/razan/fuse/m11h/`.

## A. Pipeline A and blend (CPU)

```bash
cd code/business_entity_resolution
uv venv --python 3.11 .venv && uv pip install --python .venv/bin/python -r requirements.txt
cd src
PY=../.venv/bin/python ./run_all.sh          # every stage skips if its output exists
PY=../.venv/bin/python python -m pytest -q tests
```

Single stage: `$PY -m ber.cli <stage> [--split train|test] [--force]`. Stages in order (as in `run_all.sh`):
`normalize, folds, block, blockreport, features, train` (round 1, 5 folds, OOF), `predict --split test`, `graph` (group
features on pairs with round-1 p >= 0.01), `r2feats` (soft house-number + v2 name features on those pairs), `ce`
(cross-encoder score from `src/ce_scores/`), `stack` (round 2, 3000 rounds), `decode` (isotonic + gate + expected-F, all
out-of-fold), `report`, `write`, `blend`. LightGBM runs with a fixed 16 threads (`n_jobs`): its output changes with the
thread count. `write` and `blend` run the official validator.

`write` puts the single-pipeline result in `output/matching_results.tsv`. `blend` then joins the QTpies stage-2 p in
`blend.dir` by entity ids: candidates = union of both pipelines' candidates, p = w x ours + (1 - w) x theirs (`blend.w`
is pipeline A's weight; a pair only one side scored keeps its p), isotonic + gate + expected-F decode fitted on the
QTpies live train S1, then label-free test-time calibration (`ber/calibrate.py`: an odds factor k for countries absent
from train; `unseen_k: auto` = empty-rate matching, `extra_k` = extra files at fixed k). It writes
`output/candidates/blend_*/` and copies the chosen file and the union `candidate_pairs.tsv` to `output/`.

Step D reads three step-A files:
1. **Single-pipeline file:** run `run_all.sh` once with `blend.enabled: false` (the `blend` stage is then a no-op) and
   copy `output/matching_results.tsv` to `src/razan/fuse/solo/ce_full_v1_matching_results.tsv`
   (md5 `3a0d4c771a1203acf207811ee2c8a2fe`).
2. **M10 blend:** set `blend.enabled: true` (the config as in this folder: `blend.dir` = `src/razan/` holding the M10 bundle,
   `w: 0.3`, `unseen_k: auto`, `extra_k: [0.6]`) and run `$PY -m ber.cli blend`. It writes `output/candidate_pairs.tsv`
   (md5 `5021548f879c1f8ad6fbf157e0462778`) and `output/candidates/blend_unseen_k0.6/matching_results.tsv` (France
   k 0.6): copy it to `src/razan/fuse/blends/m10_k06_matching_results.tsv` (md5 `c523954d3a2d796d4b34d66bccec26a4`).
3. **M11h blend** (after step C's M11h): copy `src/razan/ids/` and `src/razan/dropped_train_s1.parquet` into
   `src/razan/fuse/m11h/`, set `blend.dir: code/business_entity_resolution/src/razan/fuse/m11h`, `blend.w: 0.0` and
   `blend.extra_k: []`, run `$PY -m ber.cli blend`, and copy `output/candidates/blend_cal/matching_results.tsv` to
   `src/razan/fuse/blends/m11h_w00_matching_results.tsv` (md5 `e7a6eda3527f643798c82680d47d2fed`). The candidate
   file is unchanged (same pairs).

A clean-room run of step A (fresh clone, fresh environment, the dataset and the B and C outputs) reproduced the
candidate file byte for byte and the round-2 OOF to 1e-5 (0.98766 vs 0.98765); the blend files it produced are the
ones listed above. The model stages drift slightly between runs: 0.2% of the S1 rows of a blend file differed from an
earlier reference run, with links added and removed in balance.

## D. Final file (fuse)

`fuse.py` corrects a blend file with the QTpies stage-2 p: vetoes of blend links the QTpies model rejects, adds of
confident QTpies pairs on rows the blend leaves unowned (one owner per record), a third opinion from the
single-pipeline file, twin-signature vetoes and France fills (rules in the `fuse.py` docstring and the Documentation,
section 4.4). The final file takes France rows from the fuse on the M10 blend (France k 0.6) and US/India rows from the
fuse on the M11h blend. Macro F0.5 is a sum over S1s and every S1 is in one country, so the country-wise merge is exact.
Environment: `requirements_qtpies.txt`. Inputs (all written by steps A and C; md5s in `src/razan/README.md`):
`src/razan/{pred_test_s2ce.parquet, ids/}`, `src/razan/fuse/{m9, m11h, norm, solo, blends}/`.

```bash
cd code/business_entity_resolution/src/razan
COMMON="--pred fuse/m9/pred_test_s2ce.parquet --ids ids --veto France=0.7,US=0.3,India=0.3 --add France=0.99,US=0.99,India=0.99 \
  --solo fuse/solo/ce_full_v1_matching_results.tsv --veto-solo France=0.9,US=0.7,India=0.7 --add-solo France=0.9,US=0.9,India=0.9 \
  --norm fuse/norm --veto-g France=0.99 --veto-n US=0.7 --fill France=0.5"
# US/India part: fuse on the M11h blend; the US/India rules read M11h p
python src/fuse.py fuse/blends/m11h_w00_matching_results.tsv out_usin $COMMON --pred-alt fuse/m11h/pred_test_s2ce.parquet --alt-countries US,India
#   -> out_usin/matching_results.tsv  md5 10f5696b16da21ba9634ad6040110b3f
# France part: fuse on the M10 blend at France k 0.6 (France rules read M9 p)
python src/fuse.py fuse/blends/m10_k06_matching_results.tsv out_fr $COMMON --pred-alt pred_test_s2ce.parquet --alt-countries US,India
#   -> out_fr/matching_results.tsv    md5 9d47f34a88a26d2e0cbeb10b3aee29df
python src/merge_by_country.py out_fr/matching_results.tsv out_usin/matching_results.tsv ids/n_test_s1.parquet out_final --a-countries France
#   -> out_final/matching_results.tsv md5 f1754ce2ef7dad7a8df904636eec20c2  (= output/matching_results.tsv)
cp out_final/matching_results.tsv ../../../../output/matching_results.tsv
```

Then, from `<root>`: `python utils/validate_submission.py --matching output/matching_results.tsv --test-dir dataset/test`.
Every final link is a pair of `output/candidate_pairs.tsv`: the fuse adds only QTpies stage-2 pairs, which are all in
the union candidate set. `python src/fuse.py --selftest` checks the rules on a toy example.

**Determinism.** With the intermediate files of our run (md5s above and in `src/razan/README.md`), step D reproduces
the final file byte for byte (verified). The single-pipeline file of our run has md5 `3a0d4c77...`; a clean-room
rebuild gave `677f56f9bdce08a61a77f6a478492b99`, which changes 174-176 of 1,732,544 fused rows (0.01%). The GPU steps
and the multi-threaded LightGBM stages reproduce up to fp16 / cuDNN and thread-order noise (about 1e-4 of OOF F0.5), so
a full rerun from the data gives a near-identical, not byte-identical, final file.

## Hardware and time (measured)

Step A: Intel i7-11800H (16 threads), 16 GB RAM + swap (train blocking peaked at 10.4 GB RAM + 6.75 GB swap), no GPU.
Clean-room run: 320 min end to end. Development timings (about 5.2 h): normalize 7 min, blocking 92 min, features
60 min, round-1 train 52 min + OOF predict 14 min, test predict 13 min, graph 2 min, round 2 55 min, decode 4 min,
write + validation 8 min. Peak RAM about 10 GB; about 40 GB of disk for `work/`. Per-stage times are appended to
`work/reports/timings.tsv`. Step D: about 2 min per fuse run, ~5 GB RAM.
